# libertas-matter

`no_std` Matter TLV support and typed Matter operations for Libertas logical
devices. Owned decoding and the Libertas host bridge are available with the
default `alloc` feature. Const-generic read and subscription builders use
caller-selected fixed capacities, batch writes stream directly into a
caller-owned buffer, and the app-wide subscription is sent once for all
devices.

## Matter status values

`MatterStatus` is the raw `u32` a Matter client receives from the Hub. Bits 0-7
contain the Matter Interaction Model status, bits 8-15 contain the Matter
cluster status, and bits 16-31 contain a status generated by the Libertas Hub.
`frame::STATUS_SUPERSEDED` (`0x0001_0000`) rejects a queued command that was
replaced, even by an identical command, or a requested attribute value that
differs from the value finally written by the pooled Matter interaction.
Command replacement reduces device traffic; only the newest request/reference
per source is retained, including the survivor. A newer surviving request replaces
that source's older displaced reference, which receives no separate response.
A burst keeps only that peer's newest queued command; older queued references
receive no acknowledgement. Commands already sent keep their active interaction.
A retained displaced request's rejection is delivered only after the surviving
interaction completes. Every retained displaced command receives
`STATUS_SUPERSEDED`; only the surviving command receives its own success or error.
Zero is success; client applications may generally treat every nonzero value as
failure without interpreting its individual fields.

A Matter virtual device may issue only standard Matter statuses. Its response
APIs use `IMStatusCode` or the 16-bit `MatterResponseStatus`, neither of which
can carry the client-only Libertas status field.

The private Rust/Hub TLV status structure contains one context-0 `u32` field.
It does not use Matter's separate context-1 cluster-status field.
